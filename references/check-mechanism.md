# 阶段五：检查机制（幂等核验 · 兜底补发 · 日志 · 兜底任务）

背景：定时发布在无人值守会话里跑 GUI 自动化，可能只完成一部分（典型：填了标题+贴了封面就中断，留半成品草稿），且没人当场发现。架构根因是旧模式"发射后不管"：无自检、无重试、无告警，失败静默。本机制让发布"可核验、可重试、可追溯"。

## 0. 幂等预检（任何发布动作之前必做）

- 打开「作品管理」，按标题 + 发布日期核验目标文章是否已存在。
- 已存在 → 判定发布成功，**立即结束，严禁再次发布**（防重复）。
- 不存在 → 进入发布流程。
- 三个任务（发布 + 两个兜底）都先做这一步，因此多次运行绝不重复发布。

## 1. 半成品草稿清理（补发前必做）

- 打开「草稿箱」，若有同标题半成品草稿，先删除。
- 原因：从草稿箱打开的编辑页**不会**自动把正文首图识别为封面（新建文章页才会），且半成品状态易卡住；删掉后从「开始创作」新建更稳。

## 2. 发布后核验（发布动作之后必做，不可省）

- 回「作品管理」刷新列表，确认该文章（标题 + 当天日期 + 状态"审核中"/"已发布"）确实出现，记录 pgc_id，才算成功。
- 列表里没出现 → 按第 1 步清理草稿后重试，最多 2 次。

## 3. 失败告警与留痕（重试仍失败时必做）

- 不要假装成功。把卡点（哪一步、什么现象、Edge 是否登录、浏览器是否可用）追加写入核验日志：
  `D:/book-notes/发布核验日志.md`（素材根目录，以用户指定为准）。
- 明确标注"需人工介入"，并在任务最终输出里说明已完成到哪一步、需要用户做什么。

## 4. 核验日志格式

文件：`发布核验日志.md`，每条一行：

```
日期时间 | 书名 | 结果 | 备注
```

`结果` 取值：`已发布跳过` / `补发成功` / `发布成功` / `补发失败(需人工介入)`。

文件内还应维护一张 **排期对照表**，供兜底任务判断"今天该发哪本"：

```
| 日期 | 书名 | 标题 | 正文文件 | 封面文件 |
```

每次新增排期追加行；发布/核验后追加日志条目。

## 5. 独立兜底核验任务（长期无人值守时安排）

- 除发布任务外，设置两个独立 recurring automation：
  - 午间核验（如 10:30）：`FREQ=DAILY;BYHOUR=10;BYMINUTE=30`
  - 晚间终检（如 18:00）：`FREQ=DAILY;BYHOUR=18;BYMINUTE=0`
  - 用 validFrom / validUntil 限定排期有效期（排期表覆盖的日期范围）。
- 兜底任务 prompt 必须自包含：写明账号登录前提、排期对照表路径、核验日志路径、幂等 SOP 全部步骤、素材目录绝对路径（automation 的 cwds 可能被系统改写，因此 prompt 里全用绝对路径）。
- 逻辑：按"日期→书名"查排期表 → 幂等预检 → 已发则记录"已发布跳过"结束 → 未发则清草稿 → 剪贴板方案补发 → 回作品管理核验 → 写日志；仍失败则告警。
- 设计要点：兜底任务与发布任务相互独立，即便发布会话整体中断，兜底仍有独立机会发现并补救。

## 6. 诚实边界（必须向用户说明）

- 无法做到"绝对零失败"——全部自动化都依赖本地 Edge 开着且登录、浏览器自动化不中断；头条没有个人发布 API。
- 本方案 = 大幅降低失败率 + 失败可自发现自补救 + 兜底告警，不是零失败保证。
- 任务最终输出里如实写明：已完成到哪一步、发布状态、是否需人工介入；不要把计划写成成果，不要把"审核中"写成"已上线"。
